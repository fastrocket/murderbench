OFFLINE ROLLOUT KERNEL REVIEW — October 2, 2026
Scope: rollout_simulator.py, test_rollout_simulator.py and rollout-design.txt. Independently ran python -m unittest tests.test_rollout_simulator -v: all ten tests passed. No private files, model/network calls, production or spending. This is a narrow engineering review, not model results or a new numbered scorecard; prior scores remain unchanged.

DECISION: core single-threaded application-boundary prototype is useful, but acceptance of its claimed immutable logging and duplicate-update fixture semantics is pending the two fixes below. It is not a full rollout implementation or confirmatory-ready simulator.

VERIFIED CORE BEHAVIOR
Immediate atomic application checks prepared-token equality plus authoritative identity/version/validity; cached application consults its separate snapshot; ungated application intentionally can differ from oracle validity. Authority is versioned across revoke and reauthorize, so earlier tokens never become fresh tokens. Proposed wrong-recipient mutations are unauthorized under atomic checking. Explicit queued drain rechecks state at application; revocation after an application does not mutate the historical receipt. Scoped stop removes matching pending items while unrelated queued scope survives. Unavailable state separates valid-authority blocking from fail-open unauthorized application. Same-call duplicates reject changed arguments, and different call IDs cannot apply the same item twice. Returned state/receipt copies protect internal state from those particular external mutations.

BLOCKING CLAIM / CORRECTNESS GAPS
1. Events, receipts, authority, expected tokens and other mutable stores are publicly exposed as live objects. In particular sim.events is the authoritative log list, not a defensive snapshot. A consumer can mutate/delete a proposal event; the next duplicate propose then uses that altered event to validate its arguments or raises StopIteration. Deep-copying inputs into _log protects against source aliasing, not mutation through the exported log. The current test's name asserts log snapshots but only mutates inspect_state and a returned receipt, never sim.events. Acceptance: keep authoritative event/state stores private, expose defensive snapshots (or immutable event views) for supported observation, and ensure duplicate argument validation uses a private canonical call record. Add an adversarial test mutating a retrieved event and its nested token, clearing a retrieved event list, and then verifying unchanged oracle, contiguous event sequence and duplicate receipt. Do not claim protection against arbitrary Python introspection, only supported APIs.

2. revoke(subject) deduplicates only while authority is already invalid. It cannot distinguish redelivery of an earlier revocation from a genuinely new revocation after reauthorization. Trace: authorize -> revoke(update R1) -> authorize new version -> redeliver R1. Current revoke invalidates the new authorization again, although F4 says duplicate update delivery is one authoritative state change and must not create new authorization/version effects. Acceptance: give authoritative updates stable IDs or explicit expected-version semantics and retain their dispositions across reauthorization; a duplicate R1 must have no new state effect while a distinct R2 must revoke the current version. Add that reordered/redelivery trace fixture. If update redelivery is outside this kernel's scope, stop labeling the present no-op-while-invalid test as full duplicate-update/idempotent-revocation coverage and explicitly leave F4 unresolved. A real state-change request without an update ID is not inherently a duplicate.

NON-MIRROR TEST COVERAGE TO ADD
Exercise two different queued IDs for the same item, duplicate IDs before and after drain/cancel, changed arguments for a canceled ID, authoritative recipient rotation after preparation (rather than only a forged token), new-token cached rejection after reauthorization, stop after one item applies followed by queued unrelated completion, and fail-open with forged/unprepared tokens. Expected outcomes should distinguish imperfect gate behavior from authoritative validity; fault gates may intentionally apply an unauthorized proposal. Test recovery from unavailable service and verify old receipt/log labels stay unchanged after later updates. These cases probe ordering and aliasing rather than merely restating helper conditions.

PROTOTYPE LIMITS
The implementation is deliberately sequential and in memory; no concurrent atomicity guarantee is established. Queue application requires explicit drain, whereas the draft full driver promises automatic next-event/terminal application. No twelve-turn target driver, authentic-prefix cloning, interlock state/version, evidence-delivery scheduler, cancel_pending tool, reviewer labeling, factorial collection or cost ledger exists here. None is implied by passing F1-F8-shaped engineering fixtures. Stop scope persists forever, so future authorization does not reopen that scope; document whether reopening requires a distinct scope/version and review the intended F8 utility semantics. Preparation currently can produce a token in a stopped scope, which atomic/cached checks then reject; this is a blocking-cost behavior, not successful reauthorization.

The original ten fixtures provide direct evidence for the covered deterministic transitions and cost nothing in model access. They are no evidence about target-model behavior, external novelty, sample-size adequacy or funding acceptance. Manager-selected offline checks should follow fixes; full rollout freeze still requires executable complete fixtures plus independent oracle/statistical/prior-case dispositions.

KERNEL CORRECTION / NARROW ACCEPTANCE ADDENDUM — October 2, 2026
Inspected corrected rollout_simulator.py and focused adversarial fixture additions. Independently reran python -m unittest tests.test_rollout_simulator -v: all 14 tests passed. Original findings and all prior scorecards remain preserved. No private/model/network/production access or spending.

Both identified blocking gaps are closed for supported single-threaded kernel APIs. State/log stores are private; events, receipts and authority properties return defensive deep copies. Duplicate commit argument validation uses private canonical token records rather than searching externally exposed event snapshots. The repaired fixture mutates a nested retrieved proposal token, clears the snapshot list, mutates a retrieved authority snapshot and clears a retrieved receipts snapshot; subsequent duplicate receipt and sequence assertions remain correct. This supports ordinary consumer isolation, not tamper resistance against arbitrary Python introspection or mutation of private attributes.

Explicit revocation update IDs now have a persistent registry across reauthorization. Redelivered R1 does not revoke the new valid authorization, whereas distinct R2 does. Logs distinguish redelivery and include the update identity. Different-subject reuse rejects; subject lookup occurs before registration of a new explicit ID. Omitted update IDs intentionally denote new change requests, not reliable redelivery identity. This resolves the F4 semantics gap without inventing duplicate detection for anonymous requests.

Additional passing adversarial fixtures exercise queued duplicates before/after drain, different IDs for the same item, canceled-call argument changes, actual recipient rotation, cached rejection of a fresh authorized token, fail-open application of an unprepared token and recovery to valid atomic application. Historical unauthorized receipt remains unauthorized after recovery. These are concrete simulator boundary outcomes, never observations of model behavior.

CURRENT DECISION: ACCEPT the corrected offline application-boundary fixture kernel within its stated prototype scope. No blocking defect remains established in these reviewed paths. This does not accept the complete rollout driver, independent oracle/statistical validity or confirmatory collection readiness. Sequential-only operation, explicit queue drain, persistent stopped scopes, absent interlock versions/full tool driver, replay/recomputability tooling and external review remain the limitations described above. Model calls, spending, funded commitments, novelty claims and revised perfect scores are not authorized or substantiated by this acceptance.
