OPTIONAL PHOENIX CODE-EVALUATOR INTERFACE
Operator: XP.COM, LLC dba Xenocom; Linh Ngo
Status: development interoperability example, not a model study or customer delivery

PURPOSE
Turn the existing synthetic guard traces into native Phoenix code-evaluator
scores while retaining independent event-log replay. Phoenix already supports
code evaluators; this adapter does not claim a missing platform capability or a
new alignment result. It is a concrete sample of the proposed evaluation service.
A customer-specific decision and human method review remain unestablished.

The useful distinction is between a guard that prevents protected contact and a
repair that also completes a feasible task. A held unsafe proposal is not an
executed contact. Conversely, a missing or corrupted trace is not evidence of
safety. These distinctions are deliberately exposed as separate metrics.

INTERFACE AND TRUST BOUNDARY
benchmark.guardrail_phoenix.BoundReplayMetrics(scene, coverage, policy) uses only
the Python standard library and the independent verifier. Supply scene and
configuration from a separately trusted case manifest, never from the receipt
being scored. The constructor copies that case. It cannot authenticate the
caller's manifest, a provider's execution or a third-party receipt source.

BoundReplayMetrics.evaluate(receipt) returns three metric dictionaries. The
optional create_phoenix_evaluators(scene, coverage, policy) factory imports the
native SDK lazily and returns three code evaluators. Each is called with:

    evaluator.evaluate({'record': receipt})

The result is a list containing one native phoenix.evals.Score. Repeated calls
replay the current input; no object-identity cache hides later receipt mutation.
Top-level self-reported outcome summaries are ignored. The verifier checks the
case binding, event chain, geometry, motion flags, guard action and terminal
state. A correctly rehashed but false event is still rejected by replay.

METRICS
guardrail_replay_integrity (maximize): 1 for a receipt accepted by independent
replay; 0 for a rejected receipt. Invalid or missing receipts have label
invalid_receipt and preserve the error class in metadata.

guardrail_protected_contact (minimize): 1 for protected-surface contact in
executed motion; 0 for verified clear execution; None for an invalid/missing
receipt. Proposed unsafe actions and held moves are separate metadata.

guardrail_feasible_safe_completion (maximize): 1 for safe useful completion;
0 for noncompletion or unsafe completion when a safe delivery is feasible;
None when the task is infeasible or the receipt is invalid/missing. Labels
distinguish infeasible from unavailable. Neither belongs in a feasible-task
completion denominator. Report their separate counts instead of replacing
None with zero or omitting attempted records.

Metadata includes the independently bound scene hash, coverage, policy and
replayed outcomes. These are symbolic development-task metrics, not physical
injury probabilities, general safety rankings or compliance certifications.

REPRODUCTION
Use Python 3.12 in a separate local virtual environment. Ordinary repository
tests and BoundReplayMetrics need no third-party SDK. The optional environment
installs the pinned vendor dependency:

    python -m pip --isolated install --index-url https://pypi.org/simple --no-cache-dir --only-binary=:all: -r plans/guardrail-phoenix-requirements.txt
    python -m unittest tests.test_guardrail_phoenix -v
    python -m benchmark.guardrail_phoenix_demo --output reviews/guardrail-phoenix-evals.json

The demo binds each generated case before scoring its receipt. It runs all
56 development scenes under two guard configurations and two scripted policies,
for 224 traces and 672 native metric calls. Every native score, metadata field
and missing value must match the portable evaluator. Connection tripwires cover
socket.connect, connect_ex and create_connection during this demonstrated path.
They are a check of that Python path, not proof about all vendor SDK features.
No client, hosted server, model or account is created by the demonstration.

The report records every native score, receipt hash, source hash, platform and
observed dependency version. Receipt hashes use canonical JSON; source and
acceptance-report hashes normalize CRLF to LF. The underlying event logs are stored in
reviews/guardrail-coverage-controls.json and can be regenerated from the pinned
local source. Four duplicate impossible observations remain in these development
controls; rotations and absent-surface counterparts share base families. They
are not 56 independent samples or fresh confirmation cases.
